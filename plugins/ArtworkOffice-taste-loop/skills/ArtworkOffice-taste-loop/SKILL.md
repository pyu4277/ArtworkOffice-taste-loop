# ArtworkOffice-taste-loop — 취향 학습·진화 스킬

자료를 만들 때마다 ① 인터뷰로 만들 자료의 정보를 모두 얻고 → ② 만들기 전에 기존 취향을 분석해 적용 계획을 세우고 → ③ 만들면서 방향이 틀어지지 않는지 모니터링하고 사용자 검토로 피드백을 모으고 → ④ 결과물 뒤 버전별 자료와 학습 내용을 비교 분석하고 → ⑤ 완료 뒤 피드백·교훈을 정밀 분석해 저장소를 갱신한다. **갱신 = 무조건 추가가 아니다.** 품질을 떨어뜨리거나 악영향이 있을 수 있으면 반영하지 않는 판단까지 이 스킬의 일이다. 모든 단계는 **"이렇게 한다"** 로 적혀 있고, 단계마다 「완료 기준」이 있다.

## 위치 — 엔진과 데이터는 따로 있다

- **엔진** `<skill>`: 이 문서가 있는 폴더(SKILL.md, GUI-Interview.html, scripts/, starter/). 누구에게나 같다. 프로젝트 `.claude/skills/ArtworkOffice-taste-loop/`, 개인 `~/.claude/skills/ArtworkOffice-taste-loop/`, 플러그인 설치 중 어디에 있어도 된다.
- **데이터** `<store>`: 사용자마다 다르다(차원·질문 은행·취향 항목·선택별 진화 기록·교훈·실수·프로젝트 기록). 스크립트가 찾는 순서는 `TASTE_LOOP_STORE` 환경 변수 → `<프로젝트 루트>/.claude/ArtworkOffice-taste-loop-data/` → `~/.claude/ArtworkOffice-taste-loop-data/` → 없으면 `<skill>/starter/`(빈 저장소, 읽기만). 지금 어디를 쓰는지는 `python3 -I <skill>/scripts/store.py`가 알려 준다.
- **처음 쓸 때**: `python3 -I <skill>/scripts/init_store.py`(프로젝트용) 또는 `--personal`(여러 프로젝트에서 같은 취향). starter를 데이터 폴더로 복사하고, 이미 있는 파일은 덮어쓰지 않는다.
- 이 문서에서 `dimensions.json`·`questions.json`·`preferences.json`·`knowledge/…`라고 쓴 것은 **모두 `<store>` 안의 파일**이다. 갱신(6절)도 `<store>`에만 한다. 엔진 폴더(특히 플러그인 설치 폴더)에는 쓰지 않는다.
- **프로젝트별 절차** `<store>/PROJECT.md`(있으면 1절에서 반드시 읽는다): 그 프로젝트의 규칙 파일과 절 번호, 작업 폴더 구조, 파일 이름 규칙, 공유본(단일 파일) 만드는 명령, 쓰는 에이전트·브라우저·생성 도구, 커밋 메시지 형식, 규칙을 고치는 곳. 이 문서와 PROJECT.md가 다르면 **PROJECT.md와 프로젝트 규칙이 이긴다.** 취향은 규칙과 충돌하면 규칙이 이긴다.
- 작업 폴더: 자료 하나를 만드는 폴더(프로젝트 루트 기준). 스크립트의 `--lecture <작업폴더>`가 이것이다. 그 안의 `materials/`에 계획·피드백·인터뷰 파일을 둔다.

## 0. 이 스킬이 다루는 지식 — 세 층

| 층 | 무엇 | 파일 | 인터뷰에서 |
|---|---|---|---|
| **A. 차원(큰 구분)과 하위 카테고리(값)** | 프로젝트를 설명하는 좌표: 파일형식·콘텐츠 유형·목적·대상(0~3세 … 어르신)·환경·발표자 유무·전체 길이·분야·언어·형식·원자료·제약·시리즈·학습 맥락·실행 모드 | `dimensions.json` | 1부: 큰 구분부터 고른다(지난 프로젝트의 값이 기본값) |
| **B. 취향 항목(entry)** | 차원 값 조건(scope) 아래에서 안정적인 선호. "이렇게 한다" 한 문장 + 범위·세기·이유·예시·출처·상태 | `preferences.json`(정본), `questions.json`(질문 은행), `knowledge/choices.json`(선택별 진화 기록), `knowledge/00_취향_요약.md`(자동 생성) | 2부: 이번 차원 값에 **맞는 항목만** 「이번에도 그대로 / 이번엔 다르게 / 항상 바꾸기」. 값이 없는 항목만 새로 묻는다 |
| **C. 프로젝트별 결정** | 주제·범위, 구성·챕터·흐름, 챕터별 시간 배분, 원자료 배치, 문구, 생성 목록, 퀴즈 내용 | 작업 폴더 `materials/00_제작계획.md` (저장소에 넣지 않는다) | 3부 + 원자료 분석 뒤 「구성 확인」 |

규칙·절차(정확성, 원자료 전수 분석, 출처·개인정보, 파일 이름, 검수 체크리스트)는 취향이 아니다. 프로젝트 규칙 파일과 이 문서의 절차에 둔다.

**취향인가, 프로젝트별 결정인가 — 판단 기준 5개** (하나라도 "아니오"면 프로젝트별 결정으로 기록한다)
1. 안정성: 같은 차원 값이면 다음 프로젝트에서도 같은 답이 나오는가?
2. 내용 독립성: 자료의 구체 내용을 몰라도 답할 수 있는가?
3. 선호인가: 사용자의 좋아/싫어인가, 아니면 사실·제약(마감·크레딧 한도·원자료 유무)인가? 사실·제약은 차원 값이나 프로젝트 기록이다.
4. 규칙 여부: 이미 프로젝트 규칙이면 entry는 그 규칙을 가리키는 참조(`source.kind: rule`)로만 둔다.
5. 근거 세기와 반복: 1 직접 말함 > 2 여러 안 중 고름 > 3 고치라고 함 > 4 말없이 받아들임 > 5 Claude 추론. 세기 4는 항목을 만들지 않고 프로젝트 기록에 count만 올린다. 세기 5는 `proposed`로 두되 **확인 질문 없이** 기본값으로 쓴다 — 사용자가 바꾸지 않고 두 프로젝트를 지나면 `confirmed`, 바꾸면 그 기록이 보정이다(자율 진화 — 6절).

판정 결과는 여덟 가지 중 하나다: 취향 등록 / 프로젝트 기록만 / 차원 값 추가(`dimensions.json`) / 질문·선택지 추가(`questions.json`) / **선택별 진화 기록 갱신**(`knowledge/choices.json` — 그 선택을 고르면 지금 어떻게 만드는지: 방법·점검·예시·이력. 방법이 나아졌으면 version을 올린다) / 템플릿 등록(`knowledge/04_템플릿_목록.md`) / 규칙 승격 제안(프로젝트 규칙 파일 — 고치는 곳은 PROJECT.md) / 폐기. 같은 차원 값에서 **3회 반복**되거나 사용자가 "항상/앞으로도"라고 말하면 취향·템플릿 승격 후보다.

**진화의 뜻**: 참고 서랍에 지난 프로젝트를 쌓는 것으로 끝나지 않는다. 마무리 갱신은 트리의 **위쪽 구분까지** 올라간다 — 새 대상·환경·형식이 나왔으면 1부 값에, 새 질문·선택지가 필요했으면 2부에, 방법이 나아졌으면 선택별 진화 기록에. 그래서 **같은 선택을 또 골라도 다음 프로젝트는 진화한 방법으로 만들어진다.**

**「등등」 규칙**: 사용자가 「등등」·「etc」라고 쓰면, 쓴 항목 외에 중요한데 빠진 항목을 철저히 분석·추론해 채운다. 추론으로 넣은 것은 `source`를 「추론」으로 표시하고, 인터뷰나 보고에서 사용자가 확인할 수 있게 보여 준다. 차원의 값 목록과 질문 선택지는 이 규칙으로 유지한다.

**작업 환경**: 사용자가 쓰는 에이전트·브라우저 도구·생성 도구·요금 제약은 `<store>/PROJECT.md`에 적는다. 그런 도구 지침이 특정 PC에서만 성립하면 2절의 실행 모드로 푼다(클라우드에서 막지 않는다).

## 1. 시작할 때 반드시

1. **기록부터 읽는다.** `<store>/PROJECT.md`(있으면 전체), `knowledge/00_취향_요약.md` 전체, `knowledge/01_교훈_기록.md` 마지막 3건, `knowledge/05_실수_기록.md` 전체(같은 실수를 되풀이하지 않기 위해), `dimensions.json`의 차원 목록, `python3 -I <skill>/scripts/recommend.py stats`(대화 추천 적중률 · 배운 규칙 · 갈린 칸 — 같은 상황인데 다르게 끝난 것을 단서로 풀었는지 그때그때 취향으로 두었는지 · 최근 바뀐 판단). 이어서 하는 프로젝트면 그 작업 폴더의 `materials/00_제작계획.md`와 `01_피드백_기록.md`.
2. **저장소를 확인·검증한다.** `python3 -I <skill>/scripts/store.py`로 데이터 폴더를 확인한다. starter(읽기 전용)라고 나오면 사용자에게 알리고 `init_store.py`로 만든다. 그다음 `python3 -I <skill>/scripts/check_store.py` → `문제 없음`이어야 한다. 오류가 있으면 먼저 고친다(JSON이 깨진 채로 작업하지 않는다). 「옛 구조」 경고가 나오면 `python3 -I <skill>/scripts/upgrade_store.py`로 데이터 폴더를 새 구조로 올린다(기록은 지우지 않는다. 엔진을 업데이트한 뒤 한 번). 「반영 대기 구조 편집」 정보가 나오면 그 편집은 인터뷰에 이미 보이고, 파일 반영은 6절 마무리 때 한다.
3. **환경을 점검한다.** Linux·macOS·클라우드: `python3 -I <skill>/scripts/check_env.py`. Windows도 파이썬이 있으면 `python -X utf8 -I <skill>\scripts\check_env.py`, 없으면 사용자에게 `powershell -ExecutionPolicy Bypass -File <skill>\scripts\check_env.ps1` 실행을 부탁하고 결과를 붙여 받는다. 프로젝트가 꼭 갖춰야 하는 도구는 `<store>/env_tools.json`에 적으면 두 점검이 함께 판정하고, 세션 시작 요약이 「필수 중 없음」으로 알린다 — 없으면 시작 전에 설치한다(형식은 `check_env.py` 머리말). 생성·디자인 커넥터(예: Higgsfield·Figma)는 스크립트가 못 본다 — Claude가 자기 도구 목록에서 찾아 표에 보탠다. 결과 표를 계획 문서의 「환경 점검」 절에 적는다. 기준은 `knowledge/06_환경_점검_기준.md`와 PROJECT.md.
4. **실행 모드를 제안한다**(2절). 지난 프로젝트의 선택이 기본값이다. 사용자가 인터뷰 1부에서 고른다.
5. 이번 일이 **새 프로젝트 / 이어서 / 마무리** 중 무엇인지 정한다. 새 프로젝트면 3절로, 이어서면 계획 문서의 「작업현황」부터, 마무리면 6절로 간다.

완료 기준: 데이터 폴더, 환경 표, 실행 모드 제안, 적용 후보 entry 목록(`match.py`)과 충돌 목록이 보고에 있다.

## 2. 실행 모드 — 환경 지침은 강제가 아니라 선택

세션 종류는 스크립트가 안다(클라우드 `CLAUDE_CODE_REMOTE=true`, 아니면 로컬). 그 위에서 **프로젝트마다 사용자가 고른다**(차원 `exec_mode`).

| 모드 | 쓸 수 있는 것 | 못 하는 것 → 처리 |
|---|---|---|
| **클라우드** | Claude 서브에이전트 병렬(단위마다 모델·effort 선택), 연결된 커넥터(호출 가능 여부는 점검 때 확인), 웹 검색·읽기, 세션에 설치된 도구, 게시 페이지 검토 | PC에만 있는 도구(PROJECT.md에 적힌 브라우저 화면 검수·다른 에이전트·로컬 MCP 등) → **막지 않고** 계획 문서 「PC에서 할 일」에 쌓는다. 프로젝트 규칙상 대체가 금지된 것은 "못 했다"로 보고한다 |
| **PC 멀티에이전트** | 위 전부 + PC의 도구와 다른 에이전트 | 고른 단위에 필요한 도구가 없으면 **설치 뒤 시작**(설치 안내는 PROJECT.md). 사용자가 "그냥 진행"이라고 하면 그 단위만 Claude로 대체하고 계획 문서에 적는다 |
| **혼합** | 클라우드에서 계획·분석·빌드·게시, PC에서 화면 검수·PC 전용 단위 | 인수인계는 「PC에서 할 일」 목록과 커밋으로. PC 대화가 목록을 읽고 처리한 뒤 완료 표시 |

- 배정표(3.2절)에는 단위마다 **실행 환경** 칸(클라우드 가능 / PC 전용 / 둘 다)을 둔다. 클라우드 모드에서 PC 전용 단위는 「PC에서 할 일」로 보내거나, 사용자 승인 아래 Claude 서브에이전트로 대체하고 품질·비용 차이를 적는다.
- 세션 시작 훅(`scripts/session_start.sh`)은 데이터·환경 요약을 넣을 뿐 아무것도 막지 않는다. 막는 판단은 이 절에서 모드에 따라 한다.

## 3. 인터뷰 1부 → 계획 → 원자료 분석 → 구성 → 레퍼런스

### 3.0 대화로 먼저 알아보기 → 추천이 골라진 인터뷰 (엔진 1.4.0)
인터뷰 페이지를 만들기 **전에** 대화로 이번 자료가 무엇을·어떻게 해야 하는지 알아보고, 그 대화와 지난 기록으로 1·2·3부 답을 **미리 골라 둔 채** 인터뷰를 연다. 사용자는 다른 것만 바꾸면 된다. 바꾼 것은 기록되어 다음 추천이 스스로 고쳐진다 — 이 진화에 **확인 질문은 하지 않는다**(6절).
1. **대화**: 요청 원문과 지금까지의 대화를 먼저 읽고, 빠진 것만 묻는다 — 무엇을(자료 종류·파일 형식), 누구에게, 왜(목적·쓰임), 어디서 보나, 길이·마감, 원자료, 꼭 넣을 것·뺄 것. 한 번에 몇 개만, 자유롭게 답하게 묻는다(선택지를 내밀어 추측을 고르게 하지 않는다). 사용자가 "알아서"라고 하면 묻지 않고 2로.
2. **대화 요약**: `<작업폴더>/materials/인터뷰/00_대화요약.md` — 사용자 원문 인용과 거기서 정해진 것, Claude가 짐작한 것을 나눠 적는다.
3. **추천 쓰기**: `materials/인터뷰/00_추천.json`(형식은 `scripts/recommend.py` 머리말). 칸마다 값 · 한 줄 이유 · 근거(`said` 사용자가 말함 / `inferred` Claude가 짐작). 상황 신호(`signals`)에는 대화에서 나온 특징을 `tag:<낱말>`로 적는다(예: 마감 임박, 공모전, 휴대폰으로 봄). 짐작할 근거가 없는 칸은 비운다(지어내지 않는다).
4. **지난 기록으로 채우기**: `python3 -I <skill>/scripts/recommend.py suggest --from <00_추천.json> --write` — 배운 규칙이 비어 있는 칸을 채우고, 수정 요청이 섞인 강한 규칙은 짐작(`inferred`)을 이긴다. 사용자가 직접 말한 것(`said`)은 바꾸지 않는다. **같은 상황인데 다르게 끝난 칸**(사용자 결정 2026-11-09): 작업 여건·상황이 달랐다는 단서가 **확실하면**(단서가 있을 때·없을 때 각각 2번 이상, 양쪽 모두 80% 이상 한 값, 우연일 확률 10% 이하) 「단서 규칙」으로 나눠 반영하고, **애매하면** 「그때그때 취향」으로 기록만 쌓다가 한쪽으로 기울 확률이 80%를 넘으면 그 값을 미리 고른다(아직 반반이면 고르지 않는다). 단서 후보는 대화의 `tag:`, 1부 답, 페이지가 제출 때 보내는 작업 여건 `ctx:`(기기 · 시간대 · 요일 · 여는 방식)다. 작업 여건 규칙은 페이지가 열릴 때 그 자리의 여건으로 판정한다. 기록이 쌓여 판단이 바뀌면(그때그때 → 단서 등) `recommend_rules.json`의 history에 남는다 — `recommend.py stats`로 본다.
5. **검사 → 페이지**: `recommend.py check <00_추천.json>` → `build_interview.py … --recommend <00_추천.json>`(레퍼런스로 채운 답이 있으면 `--prefill`도 — 순서: 레퍼런스 채움 → 대화 추천 → 지난 프로젝트 기본값, 모두 답하지 않은 칸만). 페이지는 카드마다 「대화 추천」과 한 줄 이유, 바꾸면 「추천 → 바꿈」, 화면 위 요약판(추천 N · 그대로 · 바꿈)을 보여 주고, 대시보드에 적중률이 나온다.
6. **답을 받으면 곧바로 기록**: `python3 -I <skill>/scripts/recommend.py record <답변.json>` — 추천과 최종 답의 차이(그대로·바꿈·지움)와 추천 없이 답한 칸을 상황 신호와 함께 쌓고 규칙을 다시 배운다(같은 제출은 두 번 기록하지 않는다). 보고에 이번 적중률을 한 줄로 적는다.
7. **제작 중·뒤 수정 요청**: 사용자가 「이건 ○○로 바꿔」라고 고친 것이 질문 은행의 칸에 해당하면 `recommend.py correct --project <작업폴더> --key <dim.|asp.|pq.키> --value '<JSON 값>' --said "<사용자 원문>"` — 보통 기록의 **5배 무게**로 배운다(한 번이면 바로 규칙이 된다). 같은 요청은 6절 판정표로 취향 항목에도 반영한다.

### 3.1 인터뷰 페이지 만들기·전달·회수
1. `python3 -I <skill>/scripts/build_interview.py --lecture <작업폴더> --mode interview --out <작업폴더>/materials/인터뷰/01_제작인터뷰.html` (게시용은 `--artifact`를 붙여 다른 파일로). 지난 프로젝트 기본값을 쓰려면 `--like <작업폴더>`. 화면 순서는 첫 화면 → **레퍼런스 먼저**(3.1-0) → 1부 큰 구분 → 2부 취향 → 3부 이번 자료 → 정리·제출. 페이지는 **반응형 사이트형 앱**이다: 메뉴 줄(대시보드 · 인터뷰 · 저장소 · 도움말) · 리본(이전/다음·기본 양식·제출) · 왼쪽 **사이드 트리** · 본문. 안에 품는 것: 차원·질문·취향 항목 전부(판정은 활성 항목만, 규칙은 `match.py`와 같다) + 저장소(`knowledge/projects/*.json` 프로젝트 기록, 프로젝트 안 `materials/인터뷰/*답변*.json` 지난 답변, 선택별 진화 기록, 교훈·실수·점검표, 디자인 레퍼런스 서비스, 템플릿, 변경이력).
   - **사이드 트리**: 1부 큰 구분 → 화면 → 차원 / 2부 취향 → P1~P5 → 하위 → 질문 / 3부 이번 자료 / 참고 서랍(지난 프로젝트 · 지난 답 내역 · 취향 항목 · 교훈 · 실수 · 디자인 레퍼런스 · 템플릿 · 새 메모)을 선으로 연결해 보여 준다. ▾/▸로 접고 펼치며 「모두 접기」「모두 펼치기」「선택 펼치기 ▾」(묶음 체크 + 조건: 전부 / 답 안 한 항목만 / 학습된 값이 있는 항목만 / 지금 화면만)와 낱말 검색이 있다. 640px 이상에서는 옆으로 밀어 열리고, 좁으면 겹쳐 열린다.
   - **질문을 펼치면** 학습된 현재 값 · 이번 답 · **예시 줄**(글은 같은 문장을 스타일별로 바꾼 샘플, 시각물·영상은 코드로 그린 작은 화면 그림; 진화 기록이 있는 선택지에는 「방법 vN」) · 고른 선택의 현재 방법 · 지난 답·취향 카드가 나온다. 예시를 누르면 그 값이 답이 된다(학습값과 같으면 「그대로」, 다르면 「이번엔 다르게」, 없으면 「처음 정함」; `aspects[*].from = "example"`). 「크게 보기」·「비교에 추가」는 본문에 큰 격자로 펼친다(게시 페이지는 브라우저 팝업이 막혀 본문에 펼친다). 차원도 트리에서 바로 고른다.
   - 참고 카드는 **끌어다 질문 카드에 놓거나**(손잡이 ⠿, 좁은 화면은 끌기 시작과 함께 트리가 닫힘) 카드의 **「넣기 ▸」**로 넣을 질문을 고른다. 같은 항목의 취향·지난 답을 넣으면 답도 그 값이 된다. 다른 종류의 참고는 그 질문의 「참고」 칸에 붙는다.
   - **기본 양식**: 프로젝트 카드의 「이 양식으로 시작」 또는 첫 화면의 「기본 양식」 칸에 놓기 → 그 프로젝트의 차원 값과 적용 취향이 한 번에 채워진다. 대시보드는 지금 고른 차원 값과 비슷한 지난 프로젝트를 일치 수로 정렬해 보여 준다.
   - 서랍에 없는 참고는 「새 메모」(글 + 주소)로 적는다. 다음 인터뷰부터 카드로 쌓인다(6절 7).
   - 지난 프로젝트의 결과물은 게시 URL 링크와 파일 경로로 보여 준다(썸네일 저장은 아직 없다).
2. 전달 — 게시 페이지를 쓸 수 있으면(claude.ai 등) 게시한다: `capabilities: {db: {}, downloads: true}`, 제목은 `<자료 이름> 제작 인터뷰`. 게시 URL을 계획 문서에 적고 같은 URL로 갱신한다(먼저 읽고, 그 URL로 다시 게시 — 새 페이지를 또 만들지 않는다). 게시할 수 없으면 파일을 브라우저로 열도록 안내한다. 파일로 열어도 모든 기능이 동작하고 답은 JSON 내려받기·복사로 돌아온다.
3. 회수 — 게시 페이지: 사용자가 제출하면 페이지 저장소(collection `answers`)에서 읽어 `materials/인터뷰/01_제작인터뷰_답변.json`에 저장한다. 파일: 사용자가 내려받은 JSON을 `materials/인터뷰/`에 두거나 복사해 붙여 넣는다. 이미 답한 항목은 다시 묻지 않는다.
4. **답변 JSON 읽는 법** — 추측으로 채우지 않는다(끌어다 넣은 것으로 오해·오류 없이 시작).
   - `base_project` = 사용자가 **그 프로젝트의 설정을 기본 셋팅으로 원한다**는 뜻. 그 기록(`knowledge/projects/<id>.json`)의 차원 값·적용 항목·결정·결과·산출물을 출발점으로 삼고, 답변에서 달라진 값만 차이로 다룬다. `aspects[*].from`은 그 답이 어디서 왔는지(프로젝트 id, `entry:<id>`, `example`)다.
   - `refs[<질문>]` = 그 답의 근거로 삼은 지난 내역·레퍼런스 목록(`kind`: project · past · past_all · entry · decision · lesson · mistake · design_ref · template · new_ref). 계획 문서의 「참고」 칸에 옮기고, 제작 때 그 예시(산출물 경로·URL)를 직접 본다.
   - `new_refs` = 서랍에 없던 새 레퍼런스 메모. 계획 문서 「새 레퍼런스 메모」에 두고, 마무리(6절 7)에서 서랍에 등록한다.
   - `references` = 「레퍼런스 먼저」에서 넣은 레퍼런스(`where` 주소·파일 경로 · `note` · `follow` 따를 것: all 전체 양식 · text 글 · design 디자인 · structure 구성 · motion 움직임). `ref_none: true` = 이번엔 레퍼런스 없이. `stage: "references"` = 「레퍼런스만 먼저 보내기」(3.1-0의 첫 단계 — 계획을 세우지 말고 질문지를 채워 다시 보낸다).
   - `aspects[*].choice`: `keep` 그대로 · `change` 이번엔 다르게 · `new` 처음 정함 · `ref` **레퍼런스대로**(값이 없으면 기준표에서 정한다. `reason`은 분석 근거) · `skip` **제외**(이번 자료에 해당 없음 · 정하지 않음). 질문 메모에 파일 경로·주소를 적고 「해당 자료 참고」라고 쓴 것도 레퍼런스 지정으로 읽는다(`answers_to_plan.py`가 모은다).
   - **선택별 진화 기록을 적용한다**: 답한 값마다 `knowledge/choices.json`의 `<aspect>|<option>` 기록이 있으면 그 **지금 버전의 방법·점검**으로 만든다(계획 문서 「선택별 진화 기록 적용」 절에 자동으로 들어간다). 지난번과 같은 선택이라도 그 사이 version이 올랐으면 새 방법을 쓴다. 기록이 없는 선택은 이번에 쓴 방법을 마무리 때 처음 기록한다.
5. `python3 -I <skill>/scripts/answers_to_plan.py --lecture <작업폴더> --answers <작업폴더>/materials/인터뷰/01_제작인터뷰_답변.json` → `materials/00_제작계획.md`의 뼈대(기본 양식·**레퍼런스 먼저**(레퍼런스·메모로 지정한 참고 자료·「레퍼런스대로」 질문 → 먼저 할 일: 기준표)·사양·실행 모드·환경 점검·적용 취향(참고 칸)·처음 정한 항목·선택별 진화 기록 적용·참고로 넣은 것·새 레퍼런스 메모·프로젝트 사항·검토 일정·산출물 이름 후보)가 만들어진다. 이미 작업현황 문서가 있으면 그 문서에 같은 절을 넣는다.
6. 「이번엔 다르게」·「항상 바꾸기」로 표시된 항목은 계획 문서의 「취향 갱신 후보」에 적는다(반영은 6절에서). 「레퍼런스대로」는 그 프로젝트의 결정이다 — 같은 레퍼런스 양식이 프로젝트를 넘어 반복되면 6절에서 취향 후보로 본다.

### 3.1-0 레퍼런스 먼저 — 인터뷰 맨 앞(사용자 요청 2026-11-08)
사용자가 레퍼런스를 원한 이유: **큰 구분(1부)을 고르기 전에** 레퍼런스를 모아 둔 사이트를 둘러보며 이번엔 색다른 것이 없나 찾고, 찾으면 그것만 주면 질문지가 알아서 채워져 **그 양식대로 한번 만들어 보는 것**이다. 그래서 인터뷰 첫 화면 다음이 「레퍼런스 먼저」다(2부의 옛 P2.7 레퍼런스 질문은 질문 은행 v3에서 뺐다 — `upgrade_store.py`).
1. 화면: 레퍼런스 사이트 목록(`knowledge/03_디자인_레퍼런스_서비스.md` 표, 새 탭 링크) · 「찾은 레퍼런스」(주소·파일 경로 · 메모 · 따를 것; 서랍의 지난 프로젝트·템플릿·새 메모 카드를 끌어 놓아도 된다) · 「질문지를 어떻게 채울까요?」(레퍼런스만 먼저 보내기 / 이어서 직접 답하기 / 이번엔 레퍼런스 없이). 건너뛰어도 된다.
2. **「레퍼런스만 먼저 보내기」로 오면**(`stage: "references"`, 파일 이름 `01_제작인터뷰_답변_레퍼런스.json`): ① 레퍼런스를 끝까지 분석해 **기준표**를 먼저 만든다 → `materials/인터뷰/00_레퍼런스_기준표.md`(「따를 것」에 맞춰 글: 장당 글자 수·문장 꼴·제목 꼴·글머리·표 꼴 / 디자인: 색·글꼴·배치·여백 / 구성: 흐름·장 수 — 읽은 범위와 쪽 번호를 적는다. 실수 기록 E37: 참고 자료는 기준표로 바꿔야 지켜진다) ② 기준표로 질문지 답 초안을 쓴다 → `materials/인터뷰/00_레퍼런스_채움.json` = `{"id", "source", "doc", "references", "dimensions": {질문: 값}, "aspects": {취향 질문: {"value", "reason"}}}`(확인 못 한 질문은 넣지 않는다 — 추측으로 채우지 않는다) ③ `build_interview.py … --prefill materials/인터뷰/00_레퍼런스_채움.json`으로 같은 경로·같은 게시 URL에 다시 만든다 → 사용자가 「레퍼런스에서」 표시를 확인·수정해 제출한다. 아직 답하지 않은 칸만 채우고, 같은 판은 한 번만 채운다(사용자가 바꾼 답을 덮지 않는다).
3. **직접 답하면서** 질문마다 「레퍼런스대로」(또는 「답 안 한 것 모두 레퍼런스대로」)를 고르면 값 없이 오고, 계획 문서 「레퍼런스 먼저」 절의 표에서 기준표로 정해 확인받는다.
4. 제작 지시문(서브에이전트 포함)에 기준표를 그대로 넣고, 빌드 뒤 대조 스크립트로 지켰는지 검증한다. 레퍼런스는 영감용이다 — 다른 사람의 디자인·글을 그대로 베끼지 않고, 쓴 자산의 출처를 적는다(3.4).

### 3.1-1 인터뷰 구조 — 고른 것에 따라 다음 목록이 달라진다
- **1부 목차**: 자료 종류(파일 형식 · PDF 변환본 · 콘텐츠 형태 · 활용 목적) → 화면·지면 규격(방향 → 크기·비율) → HTML 화면 구성(파일 형식에 HTML이 있을 때만: 넘겨 보는 방식 → 화면 틀 → 목차(메뉴) 모양 → 넣을 기능) → 누가 봅니까 → … 순서와 이름은 데이터 폴더의 `dimensions.json`이 정한다.
- **보이는 조건(`when`)** 은 모든 항목에 단다: 목차·질문·선택지(1부), 묶음·취향 질문·선택지(2부), 3부 질문·선택지. `{"질문": ["값", …], …}`은 모든 질문이 맞아야, `[{…}, {…}]`은 하나만 맞아도 보인다. 위 질문에 답하기 전에는 숨는다. 목차가 숨으면 그 안의 질문도 숨는다. 고를 선택지가 하나도 안 남은 질문은 질문째 숨는다. 옛 표기 `ask_when`·`applies_when`은 "답이 없으면 보여 줌"으로 읽는다. 하위 질문 카드는 들여 쓰고 「↳ ○○을(를) 골라서 나온 질문」이라고 보여 준다.
- **기타 의견**: 질문 카드마다 선택지 바로 아래에 「기타 의견」 칸이 있고, 참고를 끌어다 넣는 칸은 그 아래(카드 맨 끝)에 있다. 사이드 트리의 같은 질문에도 같은 칸이 있어 어느 쪽에 적어도 같은 값이다. 제출 JSON의 `opinions`(`dim:<질문 id>`·`pq:<3부 질문 id>`)와 `aspects[id].note`(취향 질문)로 오고, 계획 문서의 사양 표 「참고·기타 의견」 칸과 3부 줄에 들어간다. 의견은 프로젝트 결정의 근거로 읽고, 반복되면 6절에서 질문·선택지 추가 후보로 본다.
- 숨은 질문·선택지의 답은 제출 JSON과 계획 문서에서 빠진다(페이지에는 남아 있어서 다시 고르면 살아난다). 규칙은 `scripts/structure.py`와 페이지 JS가 같다.
- 질문 은행 v4(엔진 1.4.0): 2부 P2.6 움직임 질문은 **파일 형식과 상관없이** 묻는다 — v3(1.3.0)이 파일 형식에 HTML·MP4·기타가 있을 때만 묻게 한 조건을 사용자 결정(2026-11-09 「숨기지 않음으로 되돌리기」)으로 뺐다. 콘텐츠 형태 조건은 v3 전처럼 「답하지 않았으면 보여 줌」. 옛 데이터 폴더는 `upgrade_store.py`가 올린다(사용자가 따로 단 조건은 그대로).
- 건너뛰기 단추 이름은 「제외」다(사용자 요청 2026-11-08). 제출 JSON의 값은 그대로 `skip`.
- 선택지에 `group`(묶음 제목)을 달면 그 제목 아래로 묶어 보인다.
- **선택지 예시(움직이는 HTML)**: 보고 골라야 하는 선택지(HTML 화면 구성·화면 규격·바탕색·배치·움직임·화면 속 글 등)는 선택지마다 **직접 눌러 보는 작은 화면**과 「누른 순간 / 나중에」, 판 번호(방법 vN)·판 기록·「지난 판 보기」가 붙은 카드로 나온다. 그림이 필요 없는 선택(파일 형식 등)은 글 단추 그대로. 예시는 `<skill>/starter/knowledge/demos/`(엔진 기본)와 `<store>/knowledge/demos/`(내 예시, 같은 키면 이쪽이 이긴다)에 있고, 키는 `dim.<질문>|<선택지>`·`asp.<취향 질문>|<선택지>`, 조각 규칙·검사는 `node <skill>/scripts/check_demos.js <demos 폴더>`.
- 사이드 트리는 지금 보는 목차를 빛나게(「지금」) 표시하고, 「다음/이전」으로 옮기면 그 자리를 펼쳐 따라간다.
- **1부에 다시 만들지 않는 것**: 바탕색(테마)·글꼴·장면 안 배치·움직임·글 톤은 2부 취향(P1·P2)에 있다. 화면 틀(메뉴·사이드바)은 1부 「HTML 화면 구성」, 장면 안 배치는 2부 P2.4로 나눈다.
- **사용자가 구조를 직접 고칠 때**(목차부터 선택지까지): `python3 -I <skill>/scripts/build_interview.py --lecture <작업폴더> --mode edit --out <작업폴더>/materials/인터뷰/05_구조편집.html` → 사용자가 이름·순서·추가·빼기·옮기기·보이는 조건을 고치고 JSON을 내보낸다 → `python3 -I <skill>/scripts/structure_edits.py add <내보낸 JSON>`으로 **반영 대기**에 쌓는다(편집 한 건마다 무엇을·언제·왜가 남는다. `structure_edits.py list`로 본다). 그 뒤 만드는 인터뷰 페이지와 계획 문서는 대기 중 편집을 적용해 보여 준다. 데이터 파일은 **6절 마무리 때** 반영한다.

### 3.2 배정표와 산출물 이름
- 독립 단위(자료별 분석, 장면별 코딩, 장면별 시각물, 검증)로 나누고 단위마다 **에이전트·모델·effort·예상 비용·실행 환경**을 적는다. 기본 배정표가 있으면 PROJECT.md가 가리킨다. 정확성을 책임지는 단계만 높은 effort를 쓰고, 정해진 형식을 반복하는 단계는 낮게 쓴다.
- **파일 형식**(1부 첫 질문, 여러 개): 여러 개를 고르면 **같은 내용을 확장자만 달리 동시에** 만든다는 뜻이다. 내용·구성·문구는 하나로 정하고 형식마다 같은 내용으로 만들며, 한 형식에서 고친 것은 나머지에도 똑같이 반영한다. 산출물 목록에 형식마다 한 줄씩 두고, 그 형식의 크기·비율을 함께 적는다(`answers_to_plan.py`가 채운다).
- **PDF**: HTML 자료는 언제나 PDF로 바꿀 수 있어야 한다(장면마다 한 쪽, 다 그려진 모습 + 자막). 방법은 PROJECT.md 「PDF 변환」(없으면: 장면마다 마지막 모습을 그린 인쇄용 HTML을 만들어 브라우저 「PDF로 저장」이나 문서 변환 도구로 바꾼다 — 스크립트를 실행하지 않는 변환기에 발표자료를 그대로 넣으면 첫 화면만 찍힐 수 있다). 「PDF 변환본: 이번에 함께」를 골랐으면 PDF도 산출물로 만든다. HTML이 아닌 형식의 PDF는 사용자가 그 프로그램에서 직접 저장한다.
- 최종본 파일 이름을 **지금 정한다**: 이름만 보고 무슨 결과물인지 알 수 있게(`index.html`·`final` 같은 이름 금지). 프로젝트의 이름 규칙과 검사 명령은 PROJECT.md. 공유본은 파일 하나만 보내도 열려야 하므로 형식(단일 HTML / MP4 / PDF 등)을 함께 정한다.
- 사용자에게 계획을 보이고 확인받는다(완성된 사양 전체를 보여 준다 — 추측 선택지를 내밀지 않는다).

완료 기준: 차원 값, 실행 모드, 적용 취향(처음 시도 표시), 배정표, 산출물 이름·형식, 검토 일정이 계획 문서에 있고 사용자가 확인했다.

### 3.3 원자료 분석 → 구성안 → 구성 확인 → 시간 배분
0. **원자료를 PC·드라이브에서 찾아 모아야 하면(전수조사)** 프로젝트 규칙이 정한 조사 방법을 순서 그대로 따른다. 낱말 하나로 한 번 찾고 끝내지 않는다 — 새로 드러난 이름을 다음 바퀴의 낱말로 넓히고(수렴할 때까지), 날짜와 말한 쪽(사용자 · AI · 도구)을 붙이고, 쓴 쪽이 아닌 별도 검증을 거친다.
   - 조사 · 정리 중에 생기는 **모든 결과물(보고서 · 표 · 도구 · 중간 자료 · 로그 · 임시 파일)은 그 프로젝트 폴더 안에** 만든다. PC의 다른 곳에 따로 만들지 않는다.
   - 찾은 자료는 **복사본**을 프로젝트 안에 보관한다. 원본은 옮기거나 고치지 않고, 사본마다 원래 위치 · 날짜 · 크기 · sha256 대조를 목록에 적는다.
   - 파일 이름과 자리는 프로젝트 규칙(PROJECT.md)을 따른다. 이름만 보고 무엇인지 알 수 있게 짓고, 버전은 새 파일로 남긴다. 사본 이름을 여러 개 바꿀 때는 대조표를 먼저 보여 확인받는다.
1. 원자료는 끝까지 분석하고 읽은 범위를 적는다(프로젝트 규칙이 정한 방법이 있으면 그대로). 분석 전에 문구를 쓰지 않는다.
2. 분석 결과로 **구성안 2~3개**(챕터 목록·순서·강조점)를 만든다. 구성·흐름은 프로젝트별 결정이다(저장소에 넣지 않는다).
3. `build_interview.py --mode structure --spec <구성안 JSON>`로 「구성 확인」 페이지를 만들어 사용자가 고르고 순서를 바꾸고 뺄 것을 표시하게 한다. 짧으면 대화로 확인해도 된다.
4. 확정된 구성에 **시간 배분 표**(챕터 → 섹션 → 필요하면 하위 주제, 분·초 또는 쪽)를 전체 길이(차원 `length`)에서 계산해 계획 문서에 넣는다. 발표자료는 장면 수와 장면당 초, 문서는 절별 쪽수.

### 3.4 디자인 레퍼런스 탐색 (`knowledge/03_디자인_레퍼런스_서비스.md`)
사용자가 인터뷰 「레퍼런스 먼저」(3.1-0)에서 레퍼런스를 줬으면 그 기준표가 출발점이다 — 보드는 사용자가 후보를 더 원하거나 기준표로 정하지 못한 디자인 항목이 남았을 때만 만든다. 레퍼런스를 주지 않았으면: 디자인(색·글꼴·배치·모션·구성)을 정하기 전에 서비스 2~3곳에서 후보 8~12개를 모아 **레퍼런스 보드**(`materials/인터뷰/레퍼런스보드_v1.md` 또는 `--mode review` 페이지)를 만든다. 항목마다 링크·요점·무엇을 가져올지·주의. 사용자가 👍/👎와 이유 칩을 고르면 프로젝트 기록(`P2.7.reference_board`)에 적고, 반복되는 선호는 6절에서 취향(P2.4·P2.6)으로 올린다. 레퍼런스는 영감용이고 다른 사람의 디자인을 그대로 베끼지 않는다. 가져다 쓴 자산은 출처를 적는다(적는 곳은 PROJECT.md). 브라우저 화면을 볼 수 없는 환경에서는 링크와 글 설명만 모으고 스크린샷은 「PC에서 할 일」로 보낸다. 이미지 사용 정책은 프로젝트 규칙을 따른다.

## 4. 제작 중 모니터링·검토

검토 시점은 인터뷰 3부의 `review_plan`(기본: 구성안 확정 후 / 첫 완성 장면·절 / 중간 / 최종). 시점마다 이렇게 한다.

1. **자가 점검표**를 계획 문서에 채운다: 적용 취향 각각 ✓/✗(어긴 것은 이유), 고른 선택의 진화 기록 「점검」 항목, AI스러운 말투 목록(`P1.4`) 검사, 수치·출처 정확성, 파일 이름 검사, 공유본 단일 파일 검사(명령은 PROJECT.md), 실수 기록의 「시작 전 점검표」.
2. 산출물을 사용자가 볼 수 있게 내놓는다(게시 페이지는 같은 URL 갱신, 영상·문서는 파일 전송).
3. **검토 페이지**를 만든다: `build_interview.py --mode review --spec <항목 JSON>` — 장면·절·레퍼런스 카드마다 👍/👎/수정 요청 + 이유 칩 + 메모 + 전체 평. 카드에 게시 URL·시각(`?t=`)을 링크한다.
4. 답변을 `materials/01_피드백_기록.md`에 **버전 표식**(v1, v2 …)과 함께 추가한다: 항목 · 👍/👎 · 이유 칩 · 메모 · 조치(고침/보류 이유). 이유 칩 `wrong`(사실·수치 오류)은 취향이 아니라 오류다 → `knowledge/05_실수_기록.md`에도 적는다.
5. 조치한 뒤 다음 버전을 만든다. 같은 👎가 두 번 나오면 원인을 다시 찾는다(같은 방법을 세 번 넘게 반복하지 않는다).

완료 기준: 모든 👎에 조치 또는 보류 이유가 적혀 있다. 각 검토의 버전 표식이 피드백 기록과 산출물 이름(게시 페이지 버전)에서 같다.

완료 기준: 단일 파일 검사 통과, 버전비교 문서, 산출물 목록이 있다.

## 6. 마무리·업데이트 — 기록하고 진화한다

1. **교훈·실수 분석**: 피드백 기록 전체와 버전비교를 읽고, 항목마다 0절의 판단 기준 5개로 분류한다.
2. **`materials/03_취향_업데이트_제안.md`**를 쓴다. 항목마다: 제안 문장("이렇게 한다") · 분류(0절의 여덟 가지) · 범위(scope) · 세기 · 근거(피드백 번호·원문 인용) · **회귀 확인**(같은 범위의 지난 프로젝트 결과물 중 사용자가 만족이라 한 것이 이 제안을 어기는가 → 어기면 범위 축소 또는 보류) · 판정(반영 / 범위 축소 반영 / 보류 / 미반영 + 이유).
3. 판정 규칙:

| 입력 | 판정 |
|---|---|
| 사용자가 "항상/앞으로도" 직접 말함 | `confirmed`, scope = 말한 범위(없으면 현재 차원 값), 세기 1 |
| 이번 자료에서 고치라고 함(수정 요청) | `confirmed`, scope = 현재 차원 값(좁게), 세기 3. 질문 은행 칸이면 `recommend.py correct`로도 기록(가중치 5 — 보통 기록의 5배) |
| 여러 안 중 고름 | `proposed`, 세기 2 |
| 말없이 받아들임 | 항목을 만들지 않는다. 프로젝트 기록에 count만 |
| Claude 추론 | `proposed`, 세기 5. 확인 질문 없이 기본값으로 쓴다 — 다음 두 프로젝트에서 바뀌지 않으면 `confirmed`, 바뀌면 그 값으로 보정 |
| 기존 항목과 충돌 | 범위가 더 좁으면 예외 항목으로 둘 다 유지(`conflicts`에 서로 적음). 같은 범위면 **묻지 않고** 대화 추천 기록(`recommend.py stats` — 최근 기록·수정 요청이 무거움)으로 Claude가 고르고 이유를 변경이력에 적는다. 기록으로도 갈리면 3.0의 4 기준으로 판단한다 — 확실한 단서가 있으면 그 단서로 범위를 나눠 둘 다 두고, 애매하면 그때그때 취향으로 두어 기우는 쪽을 기본값으로 쓴다. "바뀌었다"면 기존 `retired` + 새 `confirmed` |
| 회귀 확인에 걸림 | 범위 축소 또는 보류 |
| 품질 위험(정확성·규칙과 충돌, 비용 급증, 가독성·접근성 저하) | 미반영 + 이유 |
| `confirmed`이고 3회 이상·넓은 범위 | 규칙 승격 제안 — 프로젝트 규칙 파일에 반영하는 곳은 PROJECT.md |
| 사용자가 반대로 고침(수정 요청 1회) 또는 인터뷰에서 반대로 2회 | 기존 `retired`(기록은 남긴다) + 새 값 `confirmed` |

4. **자율 반영 — 확인 질문을 하지 않는다**(사용자 결정 2026-11-09: "끝날 때마다 물어보고 확인받아 진화하는 시스템이 아니고, 이때는 이렇게 했네? 저때는 같은 상황인데도 다르게 했네를 기록으로 쌓으며 추론만으로 알아서 진화하는 시스템. 정 이상하면 내가 수정 요청하는 사항은 보상 점수가 훨씬 높아 보정이 더 잘되게"). Claude가 판정표대로 바로 반영한다. 승인 페이지(`--mode approve`)·「사용자가 정할 것」 목록을 만들지 않는다(사용자가 직접 원할 때만 쓴다). 대신 ① 모든 변경을 `02_변경이력.md`에 근거와 함께 남겨 되돌릴 수 있게 하고 ② 보고의 「한 것」에 바뀐 취향·구조를 한 줄씩 적고 ③ 사용자가 나중에 고치면 그것이 가장 무거운 보정이다(3.0의 7). 반영 대기 구조 편집도 판정표대로 Claude가 `apply --yes` 또는 `reject <묶음> <이유>`로 끝낸다.
   - **버전 관리를 쓰면**: 저장소 갱신은 작업 브랜치에서 커밋 → PR(기준 브랜치로). PR 본문에는 바뀐 것과 근거만 적는다(묻는 항목 없음). 저장소 갱신 PR은 작게, 빨리 병합한다(다른 작업공간도 같은 파일을 고친다 — 실수 번호처럼 병합 때 겹침을 푼다).
5. **반영 절차**(모두 `<store>` 안): 버전 관리를 쓰면 먼저 최신에 맞춤 → **반영 대기 구조 편집**이 있으면 `python3 -I <skill>/scripts/structure_edits.py preview` 결과(편집 문장 목록 + 검사)를 제안 문서에 넣고 판정표대로 → `structure_edits.py apply --yes`(dimensions.json·questions.json 반영, 변경이력 자동 기록. 반영하지 않을 묶음은 `reject <묶음 id> <이유>`) → `preferences.json`·`dimensions.json`·`questions.json` 수정(새 항목은 끝에, id는 `<sub>-<YYMMDD>-<nn>`, 출처 필수). **`preferences.json`·`knowledge/choices.json`은 손 정렬 형식(항목마다 6줄)이라 `json.load → json.dump`로 다시 쓰지 않는다** — `python3 -I <skill>/scripts/store_write.py entry-add <항목.json>` · `entry-set <id> '{"status": "confirmed"}'` · `choice-add` · `choice-set <키> … --history "<무엇이 달라졌나>" --project <작업폴더>`로 고친 항목만 쓴다(이미 풀렸으면 `store_write.py fmt`, 확인은 `fmt --check`) → `python3 -I <skill>/scripts/check_store.py` 오류 0(요약 자동 갱신) → `knowledge/02_변경이력.md`에 한 줄 → `knowledge/01_교훈_기록.md` 맨 아래에 한 건(양식은 파일 안) → 새 실수는 `knowledge/05_실수_기록.md`(이미 있으면 확인 횟수. 번호 칸은 `E12`. 여러 작업 공간이 한 저장소를 함께 쓰면 `E?-<작업 공간>-<순번>`으로 적었다가 합칠 때 다음 번호로 바꾸고 `E12 (옛 E?-<작업 공간>-1)`처럼 옛 표기를 괄호에 남긴다 — 인터뷰 페이지는 세 형식을 모두 읽는다) → `knowledge/projects/<작업폴더>.json`(차원 값·적용 항목·결정·피드백 통계·결과·산출물·비용·PC 할 일) → 커밋(메시지 형식은 PROJECT.md, 없으면 `taste-loop: <무엇을 배웠나>`). **미반영도 이유와 함께 기록한다.** 사용자가 "항상 바꾸기"를 고른 항목도 이 절차로만 반영한다. **대화 추천 기록**: 인터뷰 답을 아직 기록하지 않았으면 `recommend.py record`, 제작 중 수정 요청은 `recommend.py correct`로 남기고 `recommend.py learn` → `check_store.py`가 기록·규칙을 함께 검사한다.
6. 새 템플릿을 만들었으면 `knowledge/04_템플릿_목록.md`에 등록한다.
7. **서랍에 쌓기**: 답변 JSON의 `new_refs`와 제작 중 새로 쓴 레퍼런스를 종류별로 등록한다 — 디자인 서비스·사이트는 `knowledge/03_디자인_레퍼런스_서비스.md` 표, 재사용 틀은 `04_템플릿_목록.md`, 좋았던·싫었던 작품 예시는 해당 entry의 `examples.liked / disliked`(경로·URL), 프로젝트 기록에는 `references`(이번에 쓴 참고 목록)와 `outcome`(사용자가 말한 만족 여부). 답변 JSON은 `materials/인터뷰/`에 그대로 둔다(다음 인터뷰의 「내역」이 읽는다). 등록하지 않기로 한 메모도 이유와 함께 교훈 기록에 남긴다.
8. **진화 점검표 — 트리의 위쪽까지 고친다.** 제안 문서 끝에 아래 일곱 줄을 두고 각각 「추가함 / 올림 / 해당 없음」을 적는다.
   1. 1부 큰 구분(`dimensions.json`): 이번에 새 대상·환경·형식·원자료·제약 값이 나왔나 → 값을 끝에 추가(「추론」 아님, 실제 나온 것만). 특정 선택에서만 필요한 질문·선택지면 `when`을 단다(모두에게 필요하면 달지 않는다).
   2. 2부 질문·선택지(`questions.json`): 묻지 못한 취향, 고를 수 없던 선택지가 있었나 → aspect·option 추가(필요하면 `when`).
   3. 선택별 진화 기록(`knowledge/choices.json`): 이번에 고른 선택지마다 — 기록이 없으면 이번 방법·점검·예시로 **처음 기록**(version 1), 있는데 방법이 나아졌으면 **version +1**과 history 한 줄(날짜·프로젝트·무엇이 달라졌나), 같으면 learned_from에 프로젝트만 추가. 다음 프로젝트가 같은 선택을 해도 이 버전으로 만든다.
   4. 취향 항목(`preferences.json`): 3항의 판정 표대로.
   5. 참고 서랍: 7항(레퍼런스 서비스·템플릿·examples·프로젝트 기록·새 메모).
   6. 프로젝트 기록(`knowledge/projects/<작업폴더>.json`): `applied_entries`·`choices_used`(고른 `<aspect>|<option>@v<version>`)·`outcome`·`deliverables`.
   7. 선택지 예시(`knowledge/demos`): 이번에 고른 선택지 가운데 **실제로 만든 모습이 예시보다 나아졌거나 달라진 것**(예: 이번 프로젝트의 위쪽 메뉴 줄·목차 트리·자막 모양)이 있으면, 결과물에서 그 부분을 16KB 이하 조각으로 줄여(개인 정보·실제 이름은 빼고) `python3 -I <skill>/scripts/demos.py add <키> <조각.html> --from <작업폴더> --what "<무엇이 달라졌나>"`로 새 판을 올린다 → `node <skill>/scripts/check_demos.js <store>/knowledge/demos` 통과. 다음 인터뷰에서는 그 모습이 예시로 나온다.
   `check_store.py`가 choices.json도 검증한다(키·version·history·출처). 점검표는 일곱 줄이다.

완료 기준: 제안 문서에 모든 항목의 판정과 이유가 있고, 저장소 검증(choices.json 포함)이 통과하고, 변경이력·교훈·프로젝트 기록이 추가됐고, 새 레퍼런스가 서랍에 등록됐고, 진화 점검표 일곱 줄이 채워졌다.

## 7. 통합·정리

프로젝트 5개마다, 또는 활성 항목이 150개를 넘으면: 같은 aspect·같은 범위의 중복을 합치고, 6개월 넘게 `proposed`인 항목을 폐기 제안하고, 3회 이상 확인된 넓은 범위 항목을 규칙 승격 제안으로 올린다. 질문 은행에서 한 번도 쓰이지 않은 질문은 지우거나 `ask_if_unknown: false`로 내린다.

## 8. 보고 양식 (모든 보고 공통)

순서: ① 한 것 ② 직접 확인한 것(무엇을 어떻게) ③ 못 한 것·막힌 것(이유) ④ 쓴 비용(생성 크레딧·유료 도구 사용·생성 횟수) ⑤ 사용자가 정할 것 → **맨 마지막에 「확인할 결과물」 표**: 경로(프로젝트 상대 경로) · 게시 URL · 한 줄 설명 · 확인 포인트 · 단일 파일 여부. 그 아래 「PC에서 할 일」 남은 수. 확인한 범위만 "확인했다"고 쓴다. 추측은 `> [확인 필요]`. 답변 언어는 사용자 취향(`P5.1.language`)을 따른다.

## 9. 습관 — 이중수행과 실수를 막는다

- 게시 전에 작업현황 문서의 URL을 찾는다. 생성 전에 생성 기록·출처 기록을 찾는다. 질문 전에 `materials/인터뷰/`의 답변 JSON을 찾는다. (같은 일을 두 번 하지 않는다)
- 커밋 전에 스테이징 범위를 확인한다. 커밋 단위는 뜻이 하나씩. 저장소 갱신은 다른 변경과 섞지 않는다.
- 저장소 파일을 고치기 전에 최신에 맞추고, 합친 뒤 `check_store.py`를 다시 돌린다.
- 경로는 변수에 담아 하나인지 확인한 뒤 쓴다. 한글·공백 경로는 따옴표.
- 환경·제품에 대한 사실은 확인한 것만 쓴다. 확인 못 하면 "확인하지 못했다"고 쓴다.
- 보조 에이전트에게는 최종 응답 언어와 인용 형식(파일:행)을 지시하고, 받은 내용을 직접 대조한 뒤 쓴다.
