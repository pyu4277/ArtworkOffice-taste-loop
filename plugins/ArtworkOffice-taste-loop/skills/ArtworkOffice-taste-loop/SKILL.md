# ArtworkOffice-taste-loop — 취향 학습·진화 스킬

자료를 만들 때마다 ① 인터뷰로 만들 자료의 정보를 모두 얻고 → ② 만들기 전에 기존 취향을 분석해 적용 계획을 세우고 → ③ 만들면서 방향이 틀어지지 않는지 모니터링하고 사용자 검토로 피드백을 모으고 → ④ 결과물 뒤 버전별 자료와 학습 내용을 비교 분석하고 → ⑤ 완료 뒤 피드백·교훈을 정밀 분석해 저장소를 갱신한다. **갱신 = 무조건 추가가 아니다.** 품질을 떨어뜨리거나 악영향이 있을 수 있으면 반영하지 않는 판단까지 이 스킬의 일이다. 모든 단계는 **"이렇게 한다"** 로 적혀 있고, 단계마다 「완료 기준」이 있다.

## 위치 — 엔진과 데이터는 따로 있다

- **엔진** `<skill>`: 이 문서가 있는 폴더(SKILL.md, GUI-Interview.html, scripts/, starter/). 누구에게나 같다. 프로젝트 `.claude/skills/ArtworkOffice-taste-loop/`, 개인 `~/.claude/skills/ArtworkOffice-taste-loop/`, 플러그인 설치 중 어디에 있어도 된다.
- **데이터** `<store>`: 사용자마다 다르다(차원·질문 은행·취향 항목·선택별 진화 기록·교훈·실수·프로젝트 기록). 스크립트가 찾는 순서는 `TASTE_LOOP_STORE` 환경 변수 → `<프로젝트 루트>/.claude/ArtworkOffice-taste-loop-data/` → `~/.claude/ArtworkOffice-taste-loop-data/` → 없으면 `<skill>/starter/`(빈 저장소, 읽기만). 지금 어디를 쓰는지는 `python3 -I <skill>/scripts/store.py`가 알려 준다.
- **처음 쓸 때**: `python3 -I <skill>/scripts/init_store.py`(프로젝트용) 또는 `--personal`(여러 프로젝트에서 같은 취향). starter를 데이터 폴더로 복사하고, 이미 있는 파일은 덮어쓰지 않는다.
- 이 문서에서 `dimensions.json`·`questions.json`·`preferences.json`·`knowledge/…`라고 쓴 것은 **모두 `<store>` 안의 파일**이다. 갱신(6절)도 `<store>`에만 한다. 엔진 폴더(특히 플러그인 설치 폴더)에는 쓰지 않는다.
- **프로젝트별 절차** `<store>/PROJECT.md`(있으면 1절에서 반드시 읽는다): 그 프로젝트의 규칙 파일과 절 번호, 작업 폴더 구조, 파일 이름 규칙, 공유본(단일 파일) 만드는 명령, 쓰는 에이전트·브라우저·생성 도구, 커밋 메시지 형식, 규칙을 고치는 곳. 이 문서와 PROJECT.md가 다르면 **PROJECT.md와 프로젝트 규칙이 이긴다.** 취향은 규칙과 충돌하면 규칙이 이긴다.
- 작업 폴더: 자료 하나를 만드는 폴더(프로젝트 루트 기준). 스크립트의 `--lecture <작업폴더>`가 이것이다. 그 안의 `materials/`에 계획·피드백·인터뷰 파일을 둔다.

## 0. 이 스킬이 다루는 지식 — 세 층

| 층 | 무엇 | 파일 | 인터뷰에서 |
|---|---|---|---|
| **A. 차원(큰 구분)과 하위 카테고리(값)** | 프로젝트를 설명하는 좌표: 자료 종류·목적·대상(0~3세 … 어르신)·환경·발표자 유무·전체 길이·분야·언어·형식·원자료·제약·시리즈·학습 맥락·실행 모드 | `dimensions.json` | 1부: 큰 구분부터 고른다(지난 프로젝트의 값이 기본값) |
| **B. 취향 항목(entry)** | 차원 값 조건(scope) 아래에서 안정적인 선호. "이렇게 한다" 한 문장 + 범위·세기·이유·예시·출처·상태 | `preferences.json`(정본), `questions.json`(질문 은행), `knowledge/choices.json`(선택별 진화 기록), `knowledge/00_취향_요약.md`(자동 생성) | 2부: 이번 차원 값에 **맞는 항목만** 「이번에도 그대로 / 이번엔 다르게 / 항상 바꾸기」. 값이 없는 항목만 새로 묻는다 |
| **C. 프로젝트별 결정** | 주제·범위, 구성·챕터·흐름, 챕터별 시간 배분, 원자료 배치, 문구, 생성 목록, 퀴즈 내용 | 작업 폴더 `materials/00_제작계획.md` (저장소에 넣지 않는다) | 3부 + 원자료 분석 뒤 「구성 확인」 |

규칙·절차(정확성, 원자료 전수 분석, 출처·개인정보, 파일 이름, 검수 체크리스트)는 취향이 아니다. 프로젝트 규칙 파일과 이 문서의 절차에 둔다.

**취향인가, 프로젝트별 결정인가 — 판단 기준 5개** (하나라도 "아니오"면 프로젝트별 결정으로 기록한다)
1. 안정성: 같은 차원 값이면 다음 프로젝트에서도 같은 답이 나오는가?
2. 내용 독립성: 자료의 구체 내용을 몰라도 답할 수 있는가?
3. 선호인가: 사용자의 좋아/싫어인가, 아니면 사실·제약(마감·크레딧 한도·원자료 유무)인가? 사실·제약은 차원 값이나 프로젝트 기록이다.
4. 규칙 여부: 이미 프로젝트 규칙이면 entry는 그 규칙을 가리키는 참조(`source.kind: rule`)로만 둔다.
5. 근거 세기와 반복: 1 직접 말함 > 2 여러 안 중 고름 > 3 고치라고 함 > 4 말없이 받아들임 > 5 Claude 추론. 세기 4는 항목을 만들지 않고 프로젝트 기록에 count만 올린다. 세기 5는 `proposed`로만 두고 사용자 확인 전에는 적용하지 않는다.

판정 결과는 여덟 가지 중 하나다: 취향 등록 / 프로젝트 기록만 / 차원 값 추가(`dimensions.json`) / 질문·선택지 추가(`questions.json`) / **선택별 진화 기록 갱신**(`knowledge/choices.json` — 그 선택을 고르면 지금 어떻게 만드는지: 방법·점검·예시·이력. 방법이 나아졌으면 version을 올린다) / 템플릿 등록(`knowledge/04_템플릿_목록.md`) / 규칙 승격 제안(프로젝트 규칙 파일 — 고치는 곳은 PROJECT.md) / 폐기. 같은 차원 값에서 **3회 반복**되거나 사용자가 "항상/앞으로도"라고 말하면 취향·템플릿 승격 후보다.

**진화의 뜻**: 참고 서랍에 지난 프로젝트를 쌓는 것으로 끝나지 않는다. 마무리 갱신은 트리의 **위쪽 구분까지** 올라간다 — 새 대상·환경·형식이 나왔으면 1부 값에, 새 질문·선택지가 필요했으면 2부에, 방법이 나아졌으면 선택별 진화 기록에. 그래서 **같은 선택을 또 골라도 다음 프로젝트는 진화한 방법으로 만들어진다.**

**「등등」 규칙**: 사용자가 「등등」·「etc」라고 쓰면, 쓴 항목 외에 중요한데 빠진 항목을 철저히 분석·추론해 채운다. 추론으로 넣은 것은 `source`를 「추론」으로 표시하고, 인터뷰나 보고에서 사용자가 확인할 수 있게 보여 준다. 차원의 값 목록과 질문 선택지는 이 규칙으로 유지한다.

**작업 환경**: 사용자가 쓰는 에이전트·브라우저 도구·생성 도구·요금 제약은 `<store>/PROJECT.md`에 적는다. 그런 도구 지침이 특정 PC에서만 성립하면 2절의 실행 모드로 푼다(클라우드에서 막지 않는다).

## 1. 시작할 때 반드시

1. **기록부터 읽는다.** `<store>/PROJECT.md`(있으면 전체), `knowledge/00_취향_요약.md` 전체, `knowledge/01_교훈_기록.md` 마지막 3건, `knowledge/05_실수_기록.md` 전체(같은 실수를 되풀이하지 않기 위해), `dimensions.json`의 차원 목록. 이어서 하는 프로젝트면 그 작업 폴더의 `materials/00_제작계획.md`와 `01_피드백_기록.md`.
2. **저장소를 확인·검증한다.** `python3 -I <skill>/scripts/store.py`로 데이터 폴더를 확인한다. starter(읽기 전용)라고 나오면 사용자에게 알리고 `init_store.py`로 만든다. 그다음 `python3 -I <skill>/scripts/check_store.py` → `문제 없음`이어야 한다. 오류가 있으면 먼저 고친다(JSON이 깨진 채로 작업하지 않는다).
3. **환경을 점검한다.** Linux·macOS·클라우드: `python3 -I <skill>/scripts/check_env.py`. Windows: 사용자에게 `powershell -ExecutionPolicy Bypass -File <skill>\scripts\check_env.ps1` 실행을 부탁하고 결과를 붙여 받는다. 생성·디자인 커넥터(예: Higgsfield·Figma)는 스크립트가 못 본다 — Claude가 자기 도구 목록에서 찾아 표에 보탠다. 결과 표를 계획 문서의 「환경 점검」 절에 적는다. 기준은 `knowledge/06_환경_점검_기준.md`와 PROJECT.md.
4. **실행 모드를 제안한다**(2절). 지난 프로젝트의 선택이 기본값이다. 사용자가 인터뷰 1부에서 고른다.
5. 이번 일이 **새 프로젝트 / 이어서 / 마무리** 중 무엇인지 정한다. 새 프로젝트면 3절로, 이어서면 계획 문서의 「작업현황」부터, 마무리면 6절로 간다.

완료 기준: 데이터 폴더, 환경 표, 실행 모드 제안, 적용 후보 entry 목록(`match.py`)과 충돌 목록이 보고에 있다.

## 2. 실행 모드 — 환경 지침은 강제가 아니라 선택

세션 종류는 스크립트가 안다(클라우드 `CLAUDE_CODE_REMOTE=true`, 아니면 로컬). 그 위에서 **프로젝트마다 사용자가 고른다**(차원 `exec_mode`).

| 모드 | 쓸 수 있는 것 | 못 하는 것 → 처리 |
|---|---|---|
| **클라우드** | Claude 서브에이전트 병렬(단위마다 모델·effort 선택), 연결된 커넥터(호출 가능 여부는 점검 때 확인), 웹 검색·읽기, 세션에 설치된 도구, 게시 페이지 검토 | PC에만 있는 도구(PROJECT.md에 적힌 브라우저 화면 검수·다른 에이전트·로컬 MCP 등) → **막지 않고** 계획 문서 「PC에서 할 일」에 쌓는다. 프로젝트 규칙상 대체가 금지된 것은 "못 했다"로 보고한다 |
| **PC 멀티에이전트** | 위 전부 + PC의 도구와 다른 에이전트 | 고른 단위에 필요한 도구가 없으면 **설치 뒤 시작**(설치 안내는 PROJECT.md). 사용자가 "그냥 진행"이라고 하면 그 단위만 Claude로 대체하고 계획 문서에 적는다 |
| **혼합** | 클라우드에서 계획·분석·빌드·게시, PC에서 화면 검수·PC 전용 단위 | 인수인계는 「PC에서 할 일」 목록과 커밋으로. PC 대화가 목록을 읽고 처리한 뒤 완료 표시 |

- 배정표(3.2절)에는 단위마다 **실행 환경** 칸(클라우드 가능 / PC 전용 / 둘 다)을 둔다. 클라우드 모드에서 PC 전용 단위는 「PC에서 할 일」로 보내거나, 사용자 승인 아래 Claude 서브에이전트로 대체하고 품질·비용 차이를 적는다.
- 세션 시작 훅(`scripts/session_start.sh`)은 데이터·환경 요약을 넣을 뿐 아무것도 막지 않는다. 막는 판단은 이 절에서 모드에 따라 한다.

## 3. 인터뷰 1부 → 계획 → 원자료 분석 → 구성 → 레퍼런스

### 3.1 인터뷰 페이지 만들기·전달·회수
1. `python3 -I <skill>/scripts/build_interview.py --lecture <작업폴더> --mode interview --out <작업폴더>/materials/인터뷰/01_제작인터뷰.html` (게시용은 `--artifact`를 붙여 다른 파일로). 지난 프로젝트 기본값을 쓰려면 `--like <작업폴더>`. 페이지는 **반응형 사이트형 앱**이다: 메뉴 줄(대시보드 · 인터뷰 · 저장소 · 도움말) · 리본(이전/다음·기본 양식·제출) · 왼쪽 **사이드 트리** · 본문. 안에 품는 것: 차원·질문·취향 항목 전부(판정은 활성 항목만, 규칙은 `match.py`와 같다) + 저장소(`knowledge/projects/*.json` 프로젝트 기록, 프로젝트 안 `materials/인터뷰/*답변*.json` 지난 답변, 선택별 진화 기록, 교훈·실수·점검표, 디자인 레퍼런스 서비스, 템플릿, 변경이력).
   - **사이드 트리**: 1부 큰 구분 → 화면 → 차원 / 2부 취향 → P1~P5 → 하위 → 질문 / 3부 이번 자료 / 참고 서랍(지난 프로젝트 · 지난 답 내역 · 취향 항목 · 교훈 · 실수 · 디자인 레퍼런스 · 템플릿 · 새 메모)을 선으로 연결해 보여 준다. ▾/▸로 접고 펼치며 「모두 접기」「모두 펼치기」「선택 펼치기 ▾」(묶음 체크 + 조건: 전부 / 답 안 한 항목만 / 학습된 값이 있는 항목만 / 지금 화면만)와 낱말 검색이 있다. 640px 이상에서는 옆으로 밀어 열리고, 좁으면 겹쳐 열린다.
   - **질문을 펼치면** 학습된 현재 값 · 이번 답 · **예시 줄**(글은 같은 문장을 스타일별로 바꾼 샘플, 시각물·영상은 코드로 그린 작은 화면 그림; 진화 기록이 있는 선택지에는 「방법 vN」) · 고른 선택의 현재 방법 · 지난 답·취향 카드가 나온다. 예시를 누르면 그 값이 답이 된다(학습값과 같으면 「그대로」, 다르면 「이번엔 다르게」, 없으면 「처음 정함」; `aspects[*].from = "example"`). 「크게 보기」·「비교에 추가」는 본문에 큰 격자로 펼친다(게시 페이지는 브라우저 팝업이 막혀 본문에 펼친다). 차원도 트리에서 바로 고른다.
   - 참고 카드는 **끌어다 질문 카드에 놓거나**(손잡이 ⠿, 좁은 화면은 끌기 시작과 함께 트리가 닫힘) 카드의 **「넣기 ▸」**로 넣을 질문을 고른다. 같은 항목의 취향·지난 답을 넣으면 답도 그 값이 된다. 다른 종류의 참고는 그 질문의 「참고」 칸에 붙는다.
   - **기본 양식**: 프로젝트 카드의 「이 양식으로 시작」 또는 첫 화면의 「기본 양식」 칸에 놓기 → 그 프로젝트의 차원 값과 적용 취향이 한 번에 채워진다. 대시보드는 지금 고른 차원 값과 비슷한 지난 프로젝트를 일치 수로 정렬해 보여 준다.
   - 서랍에 없는 참고는 「새 메모」(글 + 주소)로 적는다. 다음 인터뷰부터 카드로 쌓인다(6절 7).
   - 지난 프로젝트의 결과물은 게시 URL 링크와 파일 경로로 보여 준다(썸네일 저장은 아직 없다).
2. 전달 — 게시 페이지를 쓸 수 있으면(claude.ai 등) 게시한다: `capabilities: {db: {}, downloads: true}`, 제목은 `<자료 이름> 제작 인터뷰`. 게시 URL을 계획 문서에 적고 같은 URL로 갱신한다(먼저 읽고, 그 URL로 다시 게시 — 새 페이지를 또 만들지 않는다). 게시할 수 없으면 파일을 브라우저로 열도록 안내한다. 파일로 열어도 모든 기능이 동작하고 답은 JSON 내려받기·복사로 돌아온다.
3. 회수 — 게시 페이지: 사용자가 제출하면 페이지 저장소(collection `answers`)에서 읽어 `materials/인터뷰/01_제작인터뷰_답변.json`에 저장한다. 파일: 사용자가 내려받은 JSON을 `materials/인터뷰/`에 두거나 복사해 붙여 넣는다. 이미 답한 항목은 다시 묻지 않는다.
4. **답변 JSON 읽는 법** — 추측으로 채우지 않는다(끌어다 넣은 것으로 오해·오류 없이 시작).
   - `base_project` = 사용자가 **그 프로젝트의 설정을 기본 셋팅으로 원한다**는 뜻. 그 기록(`knowledge/projects/<id>.json`)의 차원 값·적용 항목·결정·결과·산출물을 출발점으로 삼고, 답변에서 달라진 값만 차이로 다룬다. `aspects[*].from`은 그 답이 어디서 왔는지(프로젝트 id, `entry:<id>`, `example`)다.
   - `refs[<질문>]` = 그 답의 근거로 삼은 지난 내역·레퍼런스 목록(`kind`: project · past · past_all · entry · decision · lesson · mistake · design_ref · template · new_ref). 계획 문서의 「참고」 칸에 옮기고, 제작 때 그 예시(산출물 경로·URL)를 직접 본다.
   - `new_refs` = 서랍에 없던 새 레퍼런스 메모. 계획 문서 「새 레퍼런스 메모」에 두고, 마무리(6절 7)에서 서랍에 등록한다.
   - **선택별 진화 기록을 적용한다**: 답한 값마다 `knowledge/choices.json`의 `<aspect>|<option>` 기록이 있으면 그 **지금 버전의 방법·점검**으로 만든다(계획 문서 「선택별 진화 기록 적용」 절에 자동으로 들어간다). 지난번과 같은 선택이라도 그 사이 version이 올랐으면 새 방법을 쓴다. 기록이 없는 선택은 이번에 쓴 방법을 마무리 때 처음 기록한다.
5. `python3 -I <skill>/scripts/answers_to_plan.py --lecture <작업폴더> --answers <작업폴더>/materials/인터뷰/01_제작인터뷰_답변.json` → `materials/00_제작계획.md`의 뼈대(기본 양식·사양·실행 모드·환경 점검·적용 취향(참고 칸)·처음 정한 항목·선택별 진화 기록 적용·참고로 넣은 것·새 레퍼런스 메모·프로젝트 사항·검토 일정·산출물 이름 후보)가 만들어진다. 이미 작업현황 문서가 있으면 그 문서에 같은 절을 넣는다.
6. 「이번엔 다르게」·「항상 바꾸기」로 표시된 항목은 계획 문서의 「취향 갱신 후보」에 적는다(반영은 6절에서).

### 3.2 배정표와 산출물 이름
- 독립 단위(자료별 분석, 장면별 코딩, 장면별 시각물, 검증)로 나누고 단위마다 **에이전트·모델·effort·예상 비용·실행 환경**을 적는다. 기본 배정표가 있으면 PROJECT.md가 가리킨다. 정확성을 책임지는 단계만 높은 effort를 쓰고, 정해진 형식을 반복하는 단계는 낮게 쓴다.
- 최종본 파일 이름을 **지금 정한다**: 이름만 보고 무슨 결과물인지 알 수 있게(`index.html`·`final` 같은 이름 금지). 프로젝트의 이름 규칙과 검사 명령은 PROJECT.md. 공유본은 파일 하나만 보내도 열려야 하므로 형식(단일 HTML / MP4 / PDF 등)을 함께 정한다.
- 사용자에게 계획을 보이고 확인받는다(완성된 사양 전체를 보여 준다 — 추측 선택지를 내밀지 않는다).

완료 기준: 차원 값, 실행 모드, 적용 취향(처음 시도 표시), 배정표, 산출물 이름·형식, 검토 일정이 계획 문서에 있고 사용자가 확인했다.

### 3.3 원자료 분석 → 구성안 → 구성 확인 → 시간 배분
1. 원자료는 끝까지 분석하고 읽은 범위를 적는다(프로젝트 규칙이 정한 방법이 있으면 그대로). 분석 전에 문구를 쓰지 않는다.
2. 분석 결과로 **구성안 2~3개**(챕터 목록·순서·강조점)를 만든다. 구성·흐름은 프로젝트별 결정이다(저장소에 넣지 않는다).
3. `build_interview.py --mode structure --spec <구성안 JSON>`로 「구성 확인」 페이지를 만들어 사용자가 고르고 순서를 바꾸고 뺄 것을 표시하게 한다. 짧으면 대화로 확인해도 된다.
4. 확정된 구성에 **시간 배분 표**(챕터 → 섹션 → 필요하면 하위 주제, 분·초 또는 쪽)를 전체 길이(차원 `length`)에서 계산해 계획 문서에 넣는다. 발표자료는 장면 수와 장면당 초, 문서는 절별 쪽수.

### 3.4 디자인 레퍼런스 탐색 (`knowledge/03_디자인_레퍼런스_서비스.md`)
디자인(색·글꼴·배치·모션·구성)을 정하기 전에 서비스 2~3곳에서 후보 8~12개를 모아 **레퍼런스 보드**(`materials/인터뷰/레퍼런스보드_v1.md` 또는 `--mode review` 페이지)를 만든다. 항목마다 링크·요점·무엇을 가져올지·주의. 사용자가 👍/👎와 이유 칩을 고르면 프로젝트 기록(`P2.7.reference_board`)에 적고, 반복되는 선호는 6절에서 취향(P2.4·P2.6)으로 올린다. 레퍼런스는 영감용이고 다른 사람의 디자인을 그대로 베끼지 않는다. 가져다 쓴 자산은 출처를 적는다(적는 곳은 PROJECT.md). 브라우저 화면을 볼 수 없는 환경에서는 링크와 글 설명만 모으고 스크린샷은 「PC에서 할 일」로 보낸다. 이미지 사용 정책은 프로젝트 규칙을 따른다.

## 4. 제작 중 모니터링·검토

검토 시점은 인터뷰 3부의 `review_plan`(기본: 구성안 확정 후 / 첫 완성 장면·절 / 중간 / 최종). 시점마다 이렇게 한다.

1. **자가 점검표**를 계획 문서에 채운다: 적용 취향 각각 ✓/✗(어긴 것은 이유), 고른 선택의 진화 기록 「점검」 항목, AI스러운 말투 목록(`P1.4`) 검사, 수치·출처 정확성, 파일 이름 검사, 공유본 단일 파일 검사(명령은 PROJECT.md), 실수 기록의 「시작 전 점검표」.
2. 산출물을 사용자가 볼 수 있게 내놓는다(게시 페이지는 같은 URL 갱신, 영상·문서는 파일 전송).
3. **검토 페이지**를 만든다: `build_interview.py --mode review --spec <항목 JSON>` — 장면·절·레퍼런스 카드마다 👍/👎/수정 요청 + 이유 칩 + 메모 + 전체 평. 카드에 게시 URL·시각(`?t=`)을 링크한다.
4. 답변을 `materials/01_피드백_기록.md`에 **버전 표식**(v1, v2 …)과 함께 추가한다: 항목 · 👍/👎 · 이유 칩 · 메모 · 조치(고침/보류 이유). 이유 칩 `wrong`(사실·수치 오류)은 취향이 아니라 오류다 → `knowledge/05_실수_기록.md`에도 적는다.
5. 조치한 뒤 다음 버전을 만든다. 같은 👎가 두 번 나오면 원인을 다시 찾는다(같은 방법을 세 번 넘게 반복하지 않는다).

완료 기준: 모든 👎에 조치 또는 보류 이유가 적혀 있다. 각 검토의 버전 표식이 피드백 기록과 산출물 이름(게시 페이지 버전)에서 같다.

## 5. 결과물 뒤 — 공유본과 비교 분석

1. **공유용 단일 파일**을 만든다(파일 하나만 보내도 열리게). 만드는 명령과 크기 상한은 PROJECT.md. 영상 산출물은 MP4 자체가, 문서는 PDF·DOCX·HWPX가 단일 파일이다.
2. `materials/02_버전비교.md`: v1→vN 표(바뀐 것 | 계기가 된 피드백 번호 | 결과), 학습된 취향 대비(지킨 것 / 어긴 것과 이유 / 이번에 새로 드러난 것).
3. 작업 폴더의 목차 문서와 계획 문서의 「산출물 목록」을 최종 경로로 갱신한다.

완료 기준: 단일 파일 검사 통과, 버전비교 문서, 산출물 목록이 있다.

## 6. 마무리·업데이트 — 기록하고 진화한다

1. **교훈·실수 분석**: 피드백 기록 전체와 버전비교를 읽고, 항목마다 0절의 판단 기준 5개로 분류한다.
2. **`materials/03_취향_업데이트_제안.md`**를 쓴다. 항목마다: 제안 문장("이렇게 한다") · 분류(0절의 여덟 가지) · 범위(scope) · 세기 · 근거(피드백 번호·원문 인용) · **회귀 확인**(같은 범위의 지난 프로젝트 결과물 중 사용자가 만족이라 한 것이 이 제안을 어기는가 → 어기면 범위 축소 또는 보류) · 판정(반영 / 범위 축소 반영 / 보류 / 미반영 + 이유).
3. 판정 규칙:

| 입력 | 판정 |
|---|---|
| 사용자가 "항상/앞으로도" 직접 말함 | `confirmed`, scope = 말한 범위(없으면 현재 차원 값), 세기 1 |
| 이번 자료에서 고치라고 함 | `proposed`, scope = 현재 차원 값(좁게), 세기 3 → 다음 인터뷰에서 「그대로」로 확인되면 `confirmed` |
| 여러 안 중 고름 | `proposed`, 세기 2 |
| 말없이 받아들임 | 항목을 만들지 않는다. 프로젝트 기록에 count만 |
| Claude 추론 | `proposed`, 세기 5. 확인 전에는 기본값으로만 보이고 적용하지 않는다 |
| 기존 항목과 충돌 | 범위가 더 좁으면 예외 항목으로 둘 다 유지(`conflicts`에 서로 적음). 같은 범위면 사용자에게 묻는다. "바뀌었다"면 기존 `retired` + 새 `confirmed` |
| 회귀 확인에 걸림 | 범위 축소 또는 보류 |
| 품질 위험(정확성·규칙과 충돌, 비용 급증, 가독성·접근성 저하) | 미반영 + 이유 |
| `confirmed`이고 3회 이상·넓은 범위 | 규칙 승격 제안 — 프로젝트 규칙 파일에 반영하는 곳은 PROJECT.md |
| 사용자가 반대로 말함 2회 | `retired`(기록은 남긴다) |

4. **사용자 확인**: `build_interview.py --mode approve --spec <제안 JSON>`로 승인 페이지를 만들거나 대화로 항목마다 반영/축소/보류/미반영을 받는다. 확인 없이 저장소를 바꾸지 않는다.
5. **반영 절차**(모두 `<store>` 안): 버전 관리를 쓰면 먼저 최신에 맞춤 → `preferences.json`·`dimensions.json`·`questions.json` 수정(새 항목은 끝에, id는 `<sub>-<YYMMDD>-<nn>`, 출처 필수) → `python3 -I <skill>/scripts/check_store.py` 오류 0(요약 자동 갱신) → `knowledge/02_변경이력.md`에 한 줄 → `knowledge/01_교훈_기록.md` 맨 아래에 한 건(양식은 파일 안) → 새 실수는 `knowledge/05_실수_기록.md`(이미 있으면 확인 횟수) → `knowledge/projects/<작업폴더>.json`(차원 값·적용 항목·결정·피드백 통계·결과·산출물·비용·PC 할 일) → 커밋(메시지 형식은 PROJECT.md, 없으면 `taste-loop: <무엇을 배웠나>`). **미반영도 이유와 함께 기록한다.** 사용자가 "항상 바꾸기"를 고른 항목도 이 절차로만 반영한다.
6. 새 템플릿을 만들었으면 `knowledge/04_템플릿_목록.md`에 등록한다.
7. **서랍에 쌓기**: 답변 JSON의 `new_refs`와 제작 중 새로 쓴 레퍼런스를 종류별로 등록한다 — 디자인 서비스·사이트는 `knowledge/03_디자인_레퍼런스_서비스.md` 표, 재사용 틀은 `04_템플릿_목록.md`, 좋았던·싫었던 작품 예시는 해당 entry의 `examples.liked / disliked`(경로·URL), 프로젝트 기록에는 `references`(이번에 쓴 참고 목록)와 `outcome`(사용자가 말한 만족 여부). 답변 JSON은 `materials/인터뷰/`에 그대로 둔다(다음 인터뷰의 「내역」이 읽는다). 등록하지 않기로 한 메모도 이유와 함께 교훈 기록에 남긴다.
8. **진화 점검표 — 트리의 위쪽까지 고친다.** 제안 문서 끝에 아래 여섯 줄을 두고 각각 「추가함 / 올림 / 해당 없음」을 적는다.
   1. 1부 큰 구분(`dimensions.json`): 이번에 새 대상·환경·형식·원자료·제약 값이 나왔나 → 값을 끝에 추가(「추론」 아님, 실제 나온 것만).
   2. 2부 질문·선택지(`questions.json`): 묻지 못한 취향, 고를 수 없던 선택지가 있었나 → aspect·option 추가(applies_when 포함).
   3. 선택별 진화 기록(`knowledge/choices.json`): 이번에 고른 선택지마다 — 기록이 없으면 이번 방법·점검·예시로 **처음 기록**(version 1), 있는데 방법이 나아졌으면 **version +1**과 history 한 줄(날짜·프로젝트·무엇이 달라졌나), 같으면 learned_from에 프로젝트만 추가. 다음 프로젝트가 같은 선택을 해도 이 버전으로 만든다.
   4. 취향 항목(`preferences.json`): 3항의 판정 표대로.
   5. 참고 서랍: 7항(레퍼런스 서비스·템플릿·examples·프로젝트 기록·새 메모).
   6. 프로젝트 기록(`knowledge/projects/<작업폴더>.json`): `applied_entries`·`choices_used`(고른 `<aspect>|<option>@v<version>`)·`outcome`·`deliverables`.
   `check_store.py`가 choices.json도 검증한다(키·version·history·출처).

완료 기준: 제안 문서에 모든 항목의 판정과 이유가 있고, 저장소 검증(choices.json 포함)이 통과하고, 변경이력·교훈·프로젝트 기록이 추가됐고, 새 레퍼런스가 서랍에 등록됐고, 진화 점검표 여섯 줄이 채워졌다.

## 7. 통합·정리

프로젝트 5개마다, 또는 활성 항목이 150개를 넘으면: 같은 aspect·같은 범위의 중복을 합치고, 6개월 넘게 `proposed`인 항목을 폐기 제안하고, 3회 이상 확인된 넓은 범위 항목을 규칙 승격 제안으로 올린다. 질문 은행에서 한 번도 쓰이지 않은 질문은 지우거나 `ask_if_unknown: false`로 내린다.

## 8. 보고 양식 (모든 보고 공통)

순서: ① 한 것 ② 직접 확인한 것(무엇을 어떻게) ③ 못 한 것·막힌 것(이유) ④ 쓴 비용(생성 크레딧·유료 도구 사용·생성 횟수) ⑤ 사용자가 정할 것 → **맨 마지막에 「확인할 결과물」 표**: 경로(프로젝트 상대 경로) · 게시 URL · 한 줄 설명 · 확인 포인트 · 단일 파일 여부. 그 아래 「PC에서 할 일」 남은 수. 확인한 범위만 "확인했다"고 쓴다. 추측은 `> [확인 필요]`. 답변 언어는 사용자 취향(`P5.1.language`)을 따른다.

## 9. 습관 — 이중수행과 실수를 막는다

- 게시 전에 작업현황 문서의 URL을 찾는다. 생성 전에 생성 기록·출처 기록을 찾는다. 질문 전에 `materials/인터뷰/`의 답변 JSON을 찾는다. (같은 일을 두 번 하지 않는다)
- 커밋 전에 스테이징 범위를 확인한다. 커밋 단위는 뜻이 하나씩. 저장소 갱신은 다른 변경과 섞지 않는다.
- 저장소 파일을 고치기 전에 최신에 맞추고, 합친 뒤 `check_store.py`를 다시 돌린다.
- 경로는 변수에 담아 하나인지 확인한 뒤 쓴다. 한글·공백 경로는 따옴표.
- 환경·제품에 대한 사실은 확인한 것만 쓴다. 확인 못 하면 "확인하지 못했다"고 쓴다.
- 보조 에이전트에게는 최종 응답 언어와 인용 형식(파일:행)을 지시하고, 받은 내용을 직접 대조한 뒤 쓴다.
